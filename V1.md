# Groundwork v1

What Groundwork 1.0 does, what it needs, and where it stops.

**Status: working baseline accepted; final release verification and publication are pending.** See
[Before release](#before-release).

## What v1 does

Groundwork gives developers and their coding agents shared project context: the spec, decisions, a
plan of small cards, evidence for each card and a handoff, kept as files in the repository. Any
session, tool or teammate continues from those files.

- **Commands.** Three native commands: `/gw` (says where things stand and runs the next step),
  `/gw-approve` and `/gw-reject`. Other helpers live in `.groundwork/commands/`; `/gw` reads the one it
  needs, or the human asks for it in plain words.
- **Build loop.** For each card a tester writes failing tests, an implementer makes them pass, and a
  reviewer reruns everything. Where the tool supports subagents (Claude Code, OpenCode), each role runs
  in its own fresh context; otherwise one session plays the roles in turn, loading only each role's
  files. The agent finishes all work before the approval stop.
- **Quick path.** Small changes can be committed as `[quick]` without a card; checks must still pass.
- **CLI.** `init`, `upgrade` (keeps your edits; an edited managed file gets a `.new` to merge),
  `uninstall` (keeps changed files and, with `--keep-state`, `.groundwork/`), `doctor`, `check`
  (read-only, CI-friendly), `status`, `mode`, `migrate legacy`, `reassess`, `retro`.

### Approval

The approval mode is chosen at setup and changed only by the human (`npx groundwork-ai mode`).

- **per-card** (default). The human approves each card:
  - `/gw-approve <id>` approves that card; several IDs, separated by spaces or commas, approve
    several;
  - a bare `/gw-approve` approves the one waiting card; with more than one waiting, it approves
    nothing and the agent asks which;
  - `/gw-reject <id> <reason>` sends a card back with the reason.
- **per-phase.** Cards are committed when review passes, without a per-card approval. The human then
  reviews the phase with `/gw-approve`. That sign-off is a workflow step, not something the commit
  gate enforces before the card commits.
- **at-end** (kept only for projects that already use it). `/gw-approve all` records one approval for
  every waiting card, and the gate requires it for the batch commit.

A message counts as the command only when its first line is `/gw-approve` (or `/gw-reject`) followed
by nothing but its arguments. Plain words such as "looks good, commit it" don't approve: the agent asks
for the command and changes nothing.

Where approval is enforced (per-card, and at-end's batch), it is bound to what was reviewed: the commit it was based on, the code, the card, its linked
evidence, `SPEC.md`, decisions and the task's declared context. Status, History and confirming human
checks don't count as changes. If anything else changes, the commit is refused: the human reviews the
additional changes and approves the current state only if it is acceptable. Any later message clears
a pending approval, so the approval and the commit it allows happen in the same turn.

### Enforcement

- **Commit gate.** A commit naming a card needs that card done, passing `check`, and (in per-card and
  at-end modes) approved as it is now. A commit naming no card needs an explicit tag (`[quick]`,
  `[setup]`, `[plan]`, `[docs]`, `[no-card] <reason>`), and each tag covers only its kind of change.
- **Harness protection.** Through the tools Groundwork watches, and for the operations it recognizes,
  the guard refuses edits to Groundwork's guards, hooks, approval records, plugin and hook settings,
  weakening `config.json` once setup is done, running `migrate` or `uninstall`, and removing or moving
  the folders that hold these files. See Known limitations for what it doesn't see.
- **When the guard can't run.** In Claude Code, an unreadable tool call, a missing or broken
  `config.json`, a guard that fails, or a guard that can't start all block the call. OpenCode does the
  same within a session. `doctor` says what's broken and how to restore it.

## Experimental: teams and pull requests

With `integration: "pr"`, each card gets a `gw/<id>` branch with its own handoff, `check --base`
reports a stale branch and a changed decision separately, and pull-request review is the approval.
The local gate treats task-branch commits as checkpoints, and the guard refuses the agent's pushes to `main`. The
repository's branch rules (required review, required checks, dismissing stale approvals) do the
enforcing. This is a prototype: a human review, rejection and stale-review dismissal haven't been
observed end to end.

## Supported environments

- Node.js 22 or later and Git, on Windows and Linux.
- **Claude Code 2.1.295 or later**, which blocks a call when its guard can't run (`onFailure`;
  [hooks reference](https://code.claude.com/docs/en/hooks)). On Windows it needs Git for Windows,
  because Claude Code runs hooks with Git Bash. `doctor` reports the installed version.
- **OpenCode 2.x**, verified on 2.1.0 (earlier checks on 2.0.32). Non-interactive `opencode run`
  needs `--standalone` for the project plugin to load.
- **Any other AI tool**: the plain-markdown workflow in `AGENTS.md`, with no hooks or enforcement.

Not supported: Claude Code before 2.1.295 (a guard that can't run lets the call through) and Claude
Code on Windows without Git Bash (its hooks can't run there; per Claude Code's changelog the guard
then blocks calls, which hasn't been tested). macOS is untested.

## Known limitations

- **Local hooks aren't a security boundary.** They see the tool calls the AI tool reports. Shell
  commands are read for common operations (`rm`, `mv`, redirects, `sed -i`, PowerShell item commands,
  Node write calls and more), not parsed fully; other interpreters, package scripts, aliases and Git
  plumbing aren't checked. User-level settings such as `~/.claude/settings.json` are outside the
  guard. CI and review enforce only the checks configured there.
- **Restoring an earlier Git state can undo setup.** Protection of `config.json` starts when setup is
  marked done. Checking out or resetting to an earlier commit, or stashing an uncommitted setup
  change, can restore a config where setup isn't done, which the agent may then change. The reflog
  records that it happened; it doesn't prevent it.
- **Approvals show a command, not a person.** The approval record is a local file the guard keeps the
  agent from writing, but it isn't proof that a human typed the command. In Claude Code the prompt hook sees the
  typed command. In OpenCode a command picked from the menu reaches the plugin as its expanded text,
  so Groundwork's command files start with the command line, and any top-level prompt that starts with
  it counts, including one sent by another plugin. Subagent prompts never count.
- **An OpenCode session started with the guards missing** blocks the write, edit and patch tools,
  commits, and shell commands that touch Groundwork's files or run `uninstall` or `migrate`. Other
  shell commands, including `git push`, run with a warning.
- **Coarse commit matching.** Any command containing `git … commit` is treated as a commit, so a
  harmless command can be refused.
- **Edits after approval.** Agents sometimes still change the spec or a decision after approval. The
  gate refuses the commit and the human reviews the change.
- **Agents may name a helper as a command.** After a phase closes, an agent sometimes tells you to type
  `/gw-retro` or `/gw-plan`, which don't exist; `/gw` is the way on. Agents also sometimes skip
  bookkeeping such as the phase recap in the journal; the card's work and evidence are still committed
  as approved.
- **Evaluated on one agent and model**, with short tasks. See [evals/RESULTS.md](evals/RESULTS.md).
- **Small items.** A quoted id (`/gw-approve "1.1"`) records an error instead of an approval, and the
  gate then asks for `/gw-approve 1.1`. A same-version upgrade prints "from 1.0.0 to 1.0.0".

## Not yet observed

- A person running the full build loop (setup to commit) in OpenCode on this release; the approval
  and rejection commands were exercised by a person on prepared cards.
- A human pull-request review, rejection and stale-review dismissal in team mode.
- Claude Code's observed token usage (static estimates only).
