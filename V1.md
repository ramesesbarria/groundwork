# Groundwork v1 scope and release checklist

This is the tracked release plan. The historical development notes in `.groundwork/` and `PLAN.md`
are intentionally gitignored in this repository; this file is the version that ships.

## Positioning (working draft)

Developers and their coding agents build on the project's existing knowledge and progress, across
sessions and team contributions.

## v1 outcomes

1. **Reliable behavior:** correct approval handling, meaningful evidence validation, predictable checks, and clearly stated enforcement limits.
2. **Usable workflow:** straightforward setup and resumption, a small default command surface, an appropriate path for small changes, and measured context overhead.
3. **Defined team support:** separate task handoffs, explicit context dependencies, reassessment when relevant knowledge changes, and integration with normal PR review and checks.
4. **Compatibility and upgrades:** verified Claude Code and OpenCode integrations, preserved Windows support, and a safe transition for existing and customized projects.
5. **Evidence and communication:** reproducible evaluations, accurate documentation, and positioning that matches demonstrated capabilities. Build on the calculator and todo-app experiments. Measure quality and total cost, including Groundwork's overhead.

## Release checklist

- [x] Approval is human or PR review; no self-approval; decisions stay explicit.
- [x] Evidence checks cover missing files, empty files, invalid records, and content mismatches; test execution is recorded separately. Integrity is not software correctness.
- [x] `check` is deterministic and read-only; CI separates PR-head freshness/context from merged-result tests.
- [x] Setup, resume, quick path, and the default command surface were exercised; always-loaded and task-context overhead were estimated and fresh-session OpenCode usage was observed.
- [x] Team prototype: per-task handoff, context dependencies, reassessment, PR integration, and a two-developer demo.
- [ ] Claude Code and OpenCode are verified (OpenCode is live-verified; Claude Code completed scripted live approval, commit and rejection, with stale/human-driven paths still partial); Windows works; upgrade preserves edits; uninstall is safe.
- [ ] Solo and team evals are reproducible; calculator/todo evidence is included; quality and total cost are measured.
- [ ] README/docs match behavior; threat model and migration notes are accurate.
- [ ] Version, changelog, npm, and docs are ready for a release candidate.

## Team approval model

- Local task-branch commits are checkpoints. With `integration: "pr"`, the local card commit gate does not demand a human approval line.
- Pull-request review and required checks govern integration. The repository enforces required approving reviews, required checks, an up-to-date branch, and dismissal of stale approvals.
- Groundwork checks the task record, context freshness, evidence presence, and card rules on the PR head. It does not verify that a human clicked Approve.
- Agent-written `approved by human` lines are not PR approval. Decision acceptance remains explicit and separate from integration.
- The live demo PR shows both checks passing and merge blocked by `REVIEW_REQUIRED`. Human approval, rejection with requested changes, and stale-review dismissal after a new commit are **not yet observed**; they remain repository-rule behavior to verify with a second reviewer.

## Solo approval model

- Only the human's explicit `/gw-approve <card-id>` prompt records approval; `/gw-approve all` records the at-end batch, kept only for existing at-end installations. Ordinary conversation, "looks good", `/gw-reject`, and any agent-written card line do not.
- The approval record is bound to the reviewed HEAD commit, code diff (excluding `.groundwork/`), card content (excluding status and History), the hashes of linked evidence files, and the project knowledge the work rests on: `SPEC.md`, decision records, and the task's declared context and dependency files.
- Changing the code, the card's substantive content, a linked evidence file, the spec, a decision, or declared context after approval makes the approval stale. The commit gate refuses the commit and asks for a new explicit approval.
- A card commit with no card ID is blocked unless it uses an explicit non-card tag (`[no-card] <reason>`, `[quick]`, `[setup]`, `[plan]`, `[docs]`). Each tag is limited to the kind of change it names: `[plan]` may create or edit planning records (including `SPEC.md` and decisions) but not evidence or a done card; `[setup]` may change setup files but not card or evidence work; `[quick]` may change code or docs but not a card, evidence, `SPEC.md`, a decision or context; `[no-card]` needs a reason and cannot carry card, evidence or knowledge work. The one exception is the `at-end` approval commit, which may mark approved, done cards.
- The approval file is local and gitignored. An agent can still attempt to write it through an unguarded shell; the guard blocks file writes, direct hook execution, and the normal shell paths, and the commit gate's binding limits reuse, but this is not cryptographic proof of human authorship.
- Any later human message clears the approval, so `/gw-approve` and the commit it authorizes belong in the same turn. The hook/agent flow was exercised live on OpenCode 2.0.32 with scripted prompts, not a human approval. On non-interactive `opencode run`, pass `--standalone` so the project's plugin loads; the shared background service did not load it in the 2.0.32 check. Claude Code 2.1.303 ran scripted `/gw-approve` and `/gw-reject` turns with its normal hooks and tools; approval, commit and rejection were observed. Stale approval and a human-driven Claude Code session remain unobserved.
- A card commit may include only that card and its evidence; another changed card or evidence file is refused. Staged content that differs from the working tree is refused, so the commit contains what the gate and the human reviewed. `.groundwork/private/` is never committed. A commit command that writes card, evidence, knowledge or private files in the same shell step is blocked, and Git index flags that would hide a staged change are refused.
- `at-end` is parked for v1: per-card is the default and per-phase is the optional mode. Existing at-end installations keep the batch approval behavior: `/gw-approve all`, and the final `[no-card] Approve cards` commit checks that record for every changed card, so an agent-written approval line alone cannot self-approve it.

JSON settings formatting may be normalized; user entries are preserved.

## Usability and token overhead

- The default native command surface is `/gw`, `/gw-approve` and `/gw-reject`. `gw-setup`, `gw-spec`, `gw-plan`, `gw-next`, `gw-quick`, `gw-decide`, `gw-ui-spec`, `gw-handoff` and `gw-retro` remain in `.groundwork/commands/` and `/gw` reads the one the task needs. `at-end` is parked for v1; existing installations keep it.
- Estimates use `ceil(characters / 4)`. Always-loaded before: OpenCode ≈962 tokens, Claude Code ≈1,115. After the default-surface change: OpenCode ≈655, Claude Code ≈764. `groundwork doctor` reports ≈654 always loaded on a fresh OpenCode install.
- Observed OpenCode fresh-session input was 3,726 baseline vs 4,467 with Groundwork before (delta 741), and 3,724 vs 4,464 after (delta 740). The observed fresh session did not shrink; the description-surface estimate did. Observed totals include the tool's own prompt, all turns, tool calls and cache reads, and are not a measurement of Groundwork's prompt alone.
- Task-context estimate (HANDOFF + card + implementer role + role rules): ≈693 tokens OpenCode / ≈700 Claude Code, unchanged by the surface change.
- Fresh setup via `/gw` routed to `gw-setup`, filled AGENTS/SPEC/config/HANDOFF, set `per-card`, and did not offer at-end. New-session resume read HANDOFF correctly. The quick path worked after committing setup; a request that already says to commit now counts as the quick-path OK. A normal card ran tester -> implementer -> reviewer and stopped at approval; the 1,500-token card cap forced a History trim before commit.
- Remaining friction: card History growth, the separate setup commit, and `npx` resolving a published CLI inside disposable projects. Full comparative evals remain a later milestone.

## Evidence validation and trust limits

`check` and the commit gate implement these checks:

- every linked evidence file exists and is non-empty;
- declared context dependencies match their recorded hashes;
- in solo per-card work, linked evidence file hashes match the files the human approved;
- the card's substantive content and code diff match what was approved;
- evidence changes after approval require renewed approval.

They **do not** prove that evidence is authentic, that a test command actually ran, or that the software is correct. A fabricated but non-empty file can still be linked; only review and the project's test execution can judge it. The gate inspects the tool call and the working tree; a determined agent using unobserved tools, aliases, package scripts or Git plumbing can still work around a local hook. Package scripts are not inspected, so don't add a script that runs Groundwork's approval/migration commands or `git commit`. CI and PR review are the backstop. This is the documented trust limit, not a cryptographic guarantee.

## Legacy migration

`groundwork migrate legacy --yes` records a one-time snapshot of done cards that predate the approval rule in `.groundwork/.legacy-cards.json`. It exempts only the historical "approved by human" requirement: evidence presence, invalid records, and declared-context checks still apply, and active cards are never recorded. It does not add an approval line or evidence, and it does not exempt new cards. A recorded legacy card loses the exemption if its content changes. The manifest is locked against agent writes. Dry-run first; review the list before writing.

Actual migration was exercised on a disposable copy of this repository's `.groundwork`: 44 cards were recorded, evidence (160 files), cards (61 files) and approval records were unchanged, and `check` dropped from 44 of 61 cards with problems to 5. The remaining 5 are missing or empty evidence and unchecked criteria, not approval. No non-done card was recorded.

## Prototype constraints

- Card IDs are pre-created on `main`.
- Task branches use `gw/<id>`.
- `reassess` is the helper for snapshots; `check` is read-only.
- Full team permissions, roles, dashboards, hosted services, and team workflows beyond the PR-based prototype remain non-goals.

## Migration note

The repository's older dogfood cards predate the "approved by human" rule and some evidence files are
empty. They are migration work, not evidence to be invented. Do not add historical approvals or
fabricated evidence to make them pass.
