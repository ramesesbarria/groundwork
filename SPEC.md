# Groundwork — Spec (draft 1)

> A tool-agnostic workflow for building software with AI agents:
> spec → plan → test-first build loop → human-approved ship.
> The harness learns from your mistakes and stays lean on purpose.

Status: draft · Owner: Rameses Barria · Last updated: 2026-09-24

---

## 1. What it is

Groundwork is a set of plain-markdown files plus a small CLI. You drop it into a new or existing project. It then guides you and your AI agent through the whole development cycle:

1. **Setup** — writes a lean AGENTS.md and wires up your AI tool.
2. **Spec** — turns a rough idea into a written spec through specific questions.
3. **Plan** — breaks the spec into phases and cards (small units of work).
4. **Build** — each card goes planner → tester → implementer → reviewer → you.
5. **Ship** — checks pass, the commit is made, you deploy.
6. **Learn** — repeated mistakes become notes, then rules, then guards that block them.

It works with any AI coding tool that can read markdown. Claude Code and OpenCode get first-class adapters in v1.

### Why it exists

It comes from real use. Its author built a portfolio, a church website and an event platform (Gatherin) with AI agents, hand-copying and tweaking a harness each time. The same lessons kept coming back: over-built harnesses, rules the AI forgot, lost progress at session limits, UI work that went round in circles. Groundwork packages what worked and enforces what didn't.

### How it differs from Spec Kit, BMAD and similar

| | Most harnesses | Groundwork |
|---|---|---|
| Rules | A long list with no reasons | Every rule records the mistake that created it |
| Enforcement | Written instructions | Note → rule → guard that blocks the action |
| Size | Grows forever | `doctor` measures the token cost and flags bloat |
| Tools | Usually one | Markdown core + adapters, with an eval table as proof |
| Progress | Lives in the chat | HANDOFF file, so any tool or model can resume |

## 2. Goals and non-goals

**Goals**
- A solo developer can go from idea to first approved commit in one sitting.
- Works the same on Claude Code and OpenCode (with any model, e.g. DeepSeek).
- The always-loaded harness stays small, with a token budget that is measured.
- Every "done" claim has evidence attached.
- The author's showcase: clear, demonstrable and honest.

**Non-goals (v1)**
- Teams, multi-user approval or permissions.
- Choosing a stack for the user. Groundwork lays out options and the user decides.
- Hosting, a dashboard or a cloud service.
- Running agents autonomously with no human gate.
- Parsing AI session logs (planned for later).

---

## 3. Principles

1. **Lean by default.** Start minimal and add only when a project needs it.
2. **The human approves.** By default nothing is committed without your sign-off.
3. **Guards over reminders.** If a rule matters and keeps getting broken, a guard blocks the action.
4. **Spec before code**, and a behavior spec before any UI animation.
5. **Evidence over claims.** "Done" means tests passed and there's proof.
6. **Stack-neutral.** Show trade-offs, record the user's choice, never pick silently.
7. **Plain English.** Specific questions, not "do you agree with section 2?"
8. **Resumable.** Any session can die at any point, and the next one picks up from files.

## 4. Architecture

```
┌───────────────────────────────────────────────┐
│  CORE (plain markdown, any tool can read it)  │
│  workflow · roles · templates · ledger        │
└───────────────┬───────────────────────────────┘
                │ generated by `groundwork init` / `adapter add`
      ┌─────────┴─────────┐
┌─────▼──────┐     ┌──────▼─────┐     (future: Cursor, Codex…)
│ Claude Code│     │  OpenCode  │
│  adapter   │     │  adapter   │
└────────────┘     └────────────┘

CLI (Node, cross-platform): init · adapter · status · doctor · retro
  → does deterministic work (copying, counting, parsing git).
Agent commands (/gw-*):
  → do judgment work (interviewing, planning, building, reviewing).
```

**Split of work.** Anything that must be exact (token counts, git parsing, file checks) goes in the CLI. Anything that needs judgment goes in agent commands. Without the CLI, the markdown core still works; you just lose `doctor` and automated `retro`.

**Guards** are small Node scripts in `.groundwork/guards/`. Each one takes a proposed action (a shell command, a file write) and allows or blocks it. Adapters connect them to each tool's hook system: Claude Code hooks in `settings.json`, OpenCode plugins. Writing guards in Node means they run the same on Windows, macOS and Linux.

## 5. Files in a user's project

```
AGENTS.md                      # small, always loaded; points into .groundwork/
.groundwork/
  config.json                  # approval mode, token budget, test/lint commands
  SPEC.md                      # what we're building
  HANDOFF.md                   # current state: where we are, what's next
  LESSONS.md                   # rule ledger (see §9)
  cards/
    1.1-auth-schema.md
    1.2-login-flow.md
  decisions/
    0001-database.md           # stack decisions, with trade-offs and the chosen option
  evidence/
    1.2/test-output.txt        # proof files, linked from the card
  guards/
    no-ai-trailers.mjs
  roles/
    planner.md  tester.md  implementer.md  reviewer.md
  workflow.md                  # the loop, step by step, tool-neutral

# plus the adapter output, e.g.:
.claude/skills/gw-*/SKILL.md  .claude/agents/*.md  .claude/settings.json
.opencode/…                    # equivalent commands, agents, plugins
```

AGENTS.md stays under the token budget and loads the rest only when needed. For example, the implementer reads only its own role file and the current card.

## 6. Roles

| Role | Job | Must not |
|---|---|---|
| **Planner** | Runs the spec interview, writes phases and cards with acceptance criteria and dependencies, and records stack decisions | Write code |
| **Tester** | Turns the card's acceptance criteria into failing tests | Write the implementation |
| **Implementer** | Makes the tests pass with the smallest reasonable change | Edit the tests to make them pass |
| **Reviewer** | Checks the diff against the card, the spec and LESSONS; fills in the evidence | Fix code itself; it sends the card back instead |

In tools with subagents (Claude Code, OpenCode), each role runs as a separate agent with a fresh context, so the reviewer really is "fresh eyes." In tools without them, the roles run one after another in one session, following the same role files.

## 7. Commands

Agent commands use the `gw-` prefix to avoid clashing with built-in or user commands.

| Command | What it does |
|---|---|
| `/gw-setup` | New project: short interview, then writes AGENTS.md and config. Existing project: scans the repo and drafts AGENTS.md and a "current state" spec from the code. |
| `/gw-spec` | Planner interviews you with specific questions and writes or updates SPEC.md. |
| `/gw-decide <topic>` | Presents 2–4 options with trade-offs and writes a decision record once you choose. |
| `/gw-plan` | Planner turns the spec into phases and card files, with dependencies. |
| `/gw-next` | Picks the next unblocked card and runs tester → implementer → reviewer, updating HANDOFF at each step. Stops for approval. |
| `/gw-approve` | You approve. Checks that evidence is present, then commits (and moves to the next card if configured). |
| `/gw-reject <reason>` | Sends the card back. The reason is recorded on the card and feeds `retro`. |
| `/gw-ui-spec` | Before UI or animation work: writes the states, transitions and constraints, and waits for your OK. |
| `/gw-handoff` | Writes HANDOFF.md now (also happens automatically at each role boundary). |
| `/gw-resume` | Reads HANDOFF and the current card and continues where things stopped. |
| `/gw-retro` | Reads the `groundwork retro` report and proposes ledger changes (see §9). |

CLI:

| Command | What it does |
|---|---|
| `npx groundwork init` | Copies the core into the project and asks which adapter(s) to install |
| `groundwork adapter add <tool>` | Adds or refreshes an adapter |
| `groundwork status` | Current phase, card and checks, from files |
| `groundwork doctor` | Harness health and token budget (see §10) |
| `groundwork retro` | Collects the raw signals for `/gw-retro` (see §9) |

## 8. Cards, approval and evidence

A card file:

```md
---
id: 1.2
title: Login flow
phase: 1
status: todo | testing | implementing | review | awaiting-approval | done | rejected
depends_on: [1.1]
---
## Goal
Users can log in with email + password.

## Acceptance criteria
- [ ] Wrong password shows an error, never says which field was wrong
- [ ] Session survives a page refresh

## Evidence            ← filled by tester/reviewer; /gw-approve refuses if empty
- Tests: `npm test auth` → 12 passed ([output](../evidence/1.2/test-output.txt))
- Reviewer: approved, checked against L-003, L-007
- Screenshots (UI cards): …

## History
- 2026-09-24 rejected: "error message leaks field name" → back to implementer
```

**Evidence** is saved as files in `.groundwork/evidence/<card-id>/` and linked from the card, so card files stay short.

**Commit format:** `[<card-id>] <card title>`, e.g. `[1.2] Login flow`, so every commit links back to its card.

**Approval modes** (set in `config.json`):
- `per-card` (default): you approve every card before it's committed.
- `per-phase`: cards commit on their own after review passes, and you approve the phase as a whole.

## 9. Lessons ledger and escalation ladder

`LESSONS.md` is the one place rules live. Each entry records the mistake it came from:

```md
### L-004 · No AI attribution trailers in commits
- Level: GUARD (guards/no-ai-trailers.mjs)
- Origin: 7 commits in Gatherin, 2026-09 (commit abc123…)
- History: note (09-02) → rule (09-10, repeated) → guard (09-20, repeated again)
```

**The ladder:**
1. **Note**: written down in LESSONS only, and read by the reviewer.
2. **Rule**: promoted into AGENTS.md or a role file, so it's always in context.
3. **Guard**: a script that blocks the action.

**Retro signals in v1** come from git history and Groundwork's own files only:
- reverts, and "fix" commits that touch a card's files soon after it was approved
- rejected approvals and their reasons
- reviewer findings that repeat across cards
- rules that were cited as broken more than once

`groundwork retro` collects these into a report. `/gw-retro` groups them and proposes changes such as "promote L-006 to a rule" or "add a new note." You accept or decline each one, and nothing changes without your OK.

## 10. Doctor (context budget)

`groundwork doctor` reports:
- **Always-loaded tokens**: AGENTS.md plus adapter files that load every session, checked against the budget in `config.json` (default about 2,000 tokens; the counting method is an open question).
- **Rules without an origin**: flagged, because every rule should record the mistake that created it.
- **Stale rules**: never cited by the reviewer and never triggered as a guard in N days, so they're candidates to archive.
- **Broken wiring**: an adapter that references a missing file, or a guard that isn't connected.
- **Drift**: adapter files that differ from what the core would generate.

## 11. Existing-project onboarding

`/gw-setup` on an existing repo:
1. Reads the package manifest, folder structure, tests, CI and the recent git log.
2. Drafts AGENTS.md: stack, commands and conventions it found, each marked *found* or *guessed*.
3. Drafts a "current state" SPEC.md: what the app does today, from the code.
4. Asks you to confirm anything marked *guessed*.
5. Optionally imports an existing CLAUDE.md or AGENTS.md into LESSONS as notes, with origin "imported."

## 15. Open questions

1. **Token counting**: a rough estimate (characters ÷ 4) or a real tokenizer? A real one is more accurate, but tokenizers differ by model.
2. **OpenCode details**: check the current folder names for commands, agents and plugins, and whether its plugin hooks can block a shell command the way Claude Code hooks do.
3. **UI verification**: should `gw-ui-spec` require screenshots for approval, and which tool takes them (browser MCP or Playwright)?
4. **npm package name**: `groundwork` is taken on npm (an old scaffolding tool, v0.2.1). `groundwork-ai` was free on 2026-09-24. A scoped name like `@<user>/groundwork` is the other option. The GitHub repo and brand can still be "Groundwork."
