title: "Why Groundwork"
description: "A new session, tool or model starts from zero, and a handoff written at the end of a context goes stale silently. Groundwork stamps it from git and checks it on every load."
---

A coding agent's memory is the chat. When the chat ends or fills up, what was decided, why, and where
the work stands go with it. The next session, a different tool, a different model or a teammate starts
from zero.

## The usual fix, and where it breaks

The usual fix is a handoff note the model writes at the end of its context. Two things go wrong:

1. **It is written when the model knows least about what matters**, at the end of a long context, and
   only if the model remembers to write it. Every write depends on that moment.
2. **It goes stale without anyone noticing.** It has no time, commit or branch, so three commits
   later it still reads as current, and a session acts on it with full confidence.

## What Groundwork changes

### The facts are written by the CLI, not the model

`checkpoint` stamps the handoff with the time, commit, branch, uncommitted file count, tool, model and
session, from git, and derives the journal entry from the commits. The agent supplies only prose: what
is in progress and what is next.

### Every load checks the handoff against the repository

`brief`, the session-start hook, `status` and `doctor` compare the stamp with the repository and give
one verdict (`fresh`, `behind`, `diverged`, `stale` or `unstamped`) with the concrete delta: which
commits landed, which files changed, whether files the handoff names are among them.
[Freshness →](/docs/concepts/freshness)

### Hooks save at the moments that matter

When a turn ends, before a compaction and when a session closes, a hook checkpoints, in tools that
have those events. It never claims what it doesn't know: an untouched handoff stays `behind`, and the
agent is asked once per commit to save it. Hooks never block work.

### Memory is more than the handoff

Where things are (`MAP.md`), what was decided and why (`decisions/`), what went wrong (`LESSONS.md`)
and what happened (`JOURNAL.md`) are files too, each with a token budget, so the brief stays small
and `compact` archives what grows. Nothing is deleted.

### Parallel agents don't collide

One writer per handoff. Each worker gets its own file, and a ledger records who is doing what.
[Parallel agents →](/docs/concepts/parallel-agents)

## What it is not

- **Not a framework to learn.** The one command to remember is `/gw`.
- **Not a hosted service.** Everything is files in your repo; there are no accounts or dashboards.
- **Not a guarantee the handoff is true.** Freshness is about the repository, not the truth: a handoff
  stamped at HEAD is `fresh` even if its prose is wrong.
- **Not autonomous, and not a workflow you must follow.** The development flow is optional.

## The optional flow

Groundwork's 1.0 was a development workflow: a spec, small cards, tester, implementer and reviewer
roles, approval gates and commit guards, so "done" is what the evidence shows. After real use, the part
that earned its keep was the project context, so 2.0 puts that first and keeps the workflow as an
add-on: `init --flow`, or `groundwork flow on`. [The flow →](/docs/flow)

## Who it's for

- **Developers using coding agents on ongoing projects**, who switch between sessions, tools and
  models, and want the next one to start where the last one stopped.
- **Anyone running several agents in parallel**, who needs each to have its own state.
- **Teams**, who commit the memory with the code. [Teams →](/docs/guides/teams)
