UI work goes in circles when behaviour is only described in words. So agree on it first: ask for
`gw-ui-spec` on a card before it is built.

## What gets agreed

The agent describes back to you, in plain English:

| | |
|---|---|
| **States** | Default, hover or focus, active, loading, empty, error |
| **Transitions** | What changes, how long it takes, and which elements move |
| **Constraints** | Long text, missing images, no stray scrollbars, keyboard and screen-reader use |
| **Screen sizes** | At least a phone (≈375px), a tablet (≈768px) and a desktop (≈1440px) |
| **What tests look for** | The id, label or role of each element a test will find |

It then offers two approaches with their trade-offs, says which it suggests, and waits for your OK.
No code is written before you agree.

## It becomes criteria

Each agreed behaviour goes on the card as one checkable statement:

> At 375px, the active card slides to the horizontal center; no scrollbar appears.

Each gets a way to verify it: screenshots at each screen size in `.groundwork/evidence/<card-id>/`
when the tool can take them, otherwise a manual check you can follow. Browser checks go under the
card's **How to check**, so everyone reruns the same one.

## While it is built

The [build loop](/docs/flow/the-build-loop) runs as usual, with two extra rules:

- The implementer starts the app and tries the change.
- The reviewer reruns the browser checks or drives the app itself. Reading the code isn't proof. A
  criterion that can't be checked live is marked *not verified live* and is your first caveat.

Redesigning something that works? The agent suggests committing the current state first.
