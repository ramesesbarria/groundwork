**No evidence, no approval.** "Done" is something you can check, not something the agent says.

## What counts as evidence

Files in `.groundwork/evidence/<card-id>/`, linked from the card:

- **Test output**: the command, its summary line and the failures, about 30 lines at most.
- **Screenshots** for UI work, one per screen size, when the tool can take them.
- **The reviewer's verdict**: which criteria and which lessons it checked.
- **A live check** for behaviour that only shows in the running app. Its command goes under the
  card's **How to check**, so everyone reruns the same one.

The reviewer also writes **How to check** for you: what to open, run or click. If something couldn't
be verified live, that is the first caveat you see.

## What approval refuses

`/gw-approve` runs [`groundwork check`](/docs/reference/cli#check) and stops when:

- the card's Evidence section is empty,
- a file it links to is missing, or
- a criterion is unchecked with no reason after it (`- [ ] <criterion> — <why>`).

The **commit gate** then refuses any commit that names a card unless the card is done, passes that
check, and matches your `/gw-approve <id>`. The approval is tied to what you reviewed: the commit, the
diff, the card, its evidence, the spec and the decisions it depends on. Change any of them and it
needs a new approval.

## What's enforced, and where it stops

| Area | What happens | The limit |
|---|---|---|
| Commits with no card | Refused without a tag: `[plan]`, `[docs]`, `[setup]`, `[quick]` or `[no-card] <reason>`. Each tag covers only its kind of change | |
| The quick path | A `[quick]` commit changes code without a card, so it needs no `/gw-approve` | Waiting for your OK in `per-card` mode is an instruction, not a check |
| Team projects (`integration: "pr"`) | Local commits are checkpoints; Groundwork checks the card, evidence and context on the PR head | Approval is enforced by your repository's rules, not by Groundwork |
| What the guards see | Shell commands and file writes your tool reports to them | An unwatched tool, a package script, an alias or Git plumbing can get around a local hook |
| Shell commands | Common ways of changing Groundwork's files are recognised (`rm`, `mv`, redirects, `sed -i` and more) | A command it doesn't recognise, or a script in another language, isn't checked |
| A guard that can't run | Every watched call is blocked until you repair it | In Claude Code this needs 2.1.295 or later |
| The approval record | A local file the agent is kept from writing | Not cryptographic proof that you typed it |
| Restoring old Git state | | Checking out a commit from before setup was done brings back an unprotected config |
| Evidence checks | Linked evidence exists and isn't empty; evidence changed after approval is refused | Doesn't prove a test ran or that the output is real |

CI and pull-request review are the backstop. Each tool's own limits are on its
[adapter page](/docs/adapters/claude-code).

## Baselines

A project that already has failing tests can't start from "everything passes". Setup runs the checks
once and saves the result in `.groundwork/evidence/baseline/`. From then on:

- a card passes when **nothing new fails**;
- a card that fixes a baseline failure updates the baseline;
- with no tests at all, setup asks you: add a test setup as the first card, or rely on manual checks.
